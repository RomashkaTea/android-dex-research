# Android DEX 007 format notes

These notes describe the pre-release `dex\n007\0` files in Android build
20645 for Google Sooner. The layout and opcode map were reconstructed from
that build's `lib/libdvm.so` and validated against all 51 APK/JAR files that
contain `classes.dex`.

All integers are little-endian. Offsets are absolute file offsets.

## Header and identifier tables

The header is 92 bytes:

```c
struct DexHeader007 {
    uint8_t  magic[8];           // "dex\n007\0"
    uint32_t checksum;           // Adler-32 of bytes [12, fileSize)
    uint8_t  signature[20];      // SHA-1 of bytes [32, fileSize)
    uint32_t fileSize;
    uint32_t headerSize;         // 92
    uint32_t linkSize, linkOff;
    uint32_t stringIdsSize, stringIdsOff;
    uint32_t stringObjectsSize;
    uint32_t classIdsSize, classIdsOff;
    uint32_t fieldIdsSize, fieldIdsOff;
    uint32_t methodIdsSize, methodIdsOff;
    uint32_t classDefsSize, classDefsOff;
};

struct DexStringId007 { uint32_t stringDataOff, utf16Length; };
struct DexClassId007  { uint32_t classNameIdx; };
struct DexFieldId007  { uint32_t classIdx, nameIdx, typeDescriptorIdx; };
struct DexMethodId007 { uint32_t classIdx, nameIdx, descriptorIdx; };
```

Class-ID strings are bare binary names such as `java/lang/Object`. The tool
converts those names to Smali descriptors such as `Ljava/lang/Object;`.
Field types and method descriptors are already descriptor strings.

```c
struct DexClassDef007 {
    uint32_t classIdx;
    uint32_t accessFlags;
    uint32_t superclassIdx;      // zero means no superclass
    uint32_t interfacesOff;
    uint32_t staticFieldsOff;
    uint32_t instanceFieldsOff;
    uint32_t directMethodsOff;
    uint32_t virtualMethodsOff;
};
```

String data is directly NUL-terminated modified UTF-8. Its UTF-16 length is
stored in the string-ID record, not as a ULEB128 prefix.

## Variable tables and code

```c
struct DexClassList007 {
    uint32_t size;
    uint32_t classIdx[size];
};

struct DexInstanceFieldList007 {
    uint32_t size;
    struct { uint32_t fieldIdx, accessFlags; } entries[size];
};

struct DexStaticFieldList007 {
    uint32_t size;
    struct {
        uint32_t fieldIdx, accessFlags;
        uint64_t constantValue;
    } entries[size];
};

struct DexMethodList007 {
    uint32_t size;
    struct { uint32_t methodIdx, accessFlags, codeOff; } entries[size];
};

struct DexCode007 {
    uint16_t registersSize, insSize, outsSize, padding;
    uint32_t sourceFileIdx;
    uint32_t insnsOff;
    uint32_t exceptionsOff;
    uint32_t positionsOff;
    uint32_t localsOff;
};
```

Instruction lists and exception records match the early fixed-width DEX 012
forms. DEX 007 has separate fixed-width debug tables:

```c
struct DexPositionList007 {
    uint32_t size;
    struct { uint32_t address; uint16_t line; } entries[size];
};

struct DexLocalList007 {
    uint32_t size;
    struct {
        uint32_t startAddress, endAddress;
        uint32_t nameIdx, descriptorIdx, registerNumber;
    } entries[size];
};
```

## Opcode map

The physical opcode map comes from the 256-entry dispatch table used by
`dvmInterpretStd`. Most instruction encodings are shared with DEX 012, but
the opcode numbers differ in several ranges:

- `0x00` through `0x2c` retain their logical meanings.
- Physical `0x2d` through `0x71` map to logical opcodes `0x2e` through `0x72`.
- Physical `0x72` through `0x76` are the five range invokes, logically
  `0x74` through `0x78`.
- `0x77` through `0x7a` are unused.
- `0x7b` through `0xe2` retain their logical meanings.
- `0xe3` through `0xf1` are unused.
- `0xf2` through `0xfb` are quick field and quick invoke opcodes.
- `0xfc` through `0xff` are unused.

Packed and sparse switch payloads use the `0x0100` and `0x0200` signatures.
Their targets are signed 16-bit code-unit offsets relative to the switch
instruction, as in DEX 012.

## Using the tool

```sh
python3 tools/dex007.py -H app/Calculator.apk
python3 tools/dex007.py -d --class-filter 'Calculator;' app/Calculator.apk
python3 tools/dex007.py --smali-out out/smali app/Calculator.apk
python3 tools/smali007.py out/smali -o out/classes.dex
python3 tools/dex007.py --validate --json javalib/core.jar
python3 -m unittest tools/test_dex007.py
DEX007_CORPUS=/path/to/20645 python3 -m unittest tools/test_dex007.py
```

The parser accepts raw DEX files and APK/JAR containers. Validation walks
every referenced identifier, class, field, method, code, exception, position,
local, instruction, branch, and switch payload. It also exposes SHA-1 and
Adler-32 integrity status.

`--smali-out` converts bare class names, primitive array opcodes, special
constants, branches, catches, and switch payloads to conventional Smali. The
entire Calculator output round-trips through `smali007.py` to the same class,
method, code-item, instruction, payload, and branch counts.

## Smali-to-DEX 007 assembly

`tools/smali007.py` emits native DEX 007 files. It builds bare-name class IDs,
the 92-byte header, 32-byte class definitions, unpadded static-field lists,
12-byte method records, 28-byte code records, early switch payloads, and the
physical DEX 007 opcode map. Generated SHA-1 signatures and Adler-32 checksums
are verified by reparsing the result before it is written.

```sh
python3 tools/dex007.py app/Calculator.apk --smali-out out/smali
python3 tools/smali007.py out/smali -o out/classes.dex
python3 tools/dex007.py out/classes.dex --validate
```

Existing output files are protected unless `--force` is passed.
`--no-validate` is available for malformed-file research. DEX 007 has no
declared-thrown-exception field, so the assembler rejects Smali `Throws`
annotations instead of silently discarding them. Optimized instructions that
do not exist in the DEX 007 interpreter, including `execute-inline`, are also
rejected.

The 702-class DEX 007 `core.jar` has been exported and reassembled with
identical class, method, code-item, instruction/payload, payload, and branch
counts.
